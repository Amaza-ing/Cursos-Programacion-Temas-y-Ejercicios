# Topic 03 — Privacy, security, limits and responsible use of AI

## 1. Objective of the topic

In the previous topics we have seen what generative AI is and how the Copilot ecosystem is organized. In this topic we are going to work on a fundamental part: how to use these tools safely, responsibly and professionally.

Copilot can greatly speed up work, but it can also generate errors, propose unsafe solutions, or receive information that we should not share. Therefore, before delving into GitHub Copilot and Microsoft Copilot, it is necessary to establish some basic rules of use.

Upon finishing this topic you should be able to:

- Identify what information should not be shared with an AI tool.
- Understand the difference between prompt, context and sensitive data.
- Recognize the main risks of responses generated by AI.
- Review code generated by Copilot with technical criteria.
- Apply a basic security, privacy and quality checklist.
- Use Copilot responsibly in a professional environment.

---

## 2. Why this topic is important

Generative AI can give a false sense of security. Many answers are well written, seem logical, and presented with confidence. However, that does not guarantee that they are correct.

In a professional environment, accepting an answer without reviewing it can lead to problems such as:

- Code that does not work.
- Unsafe code.
- Loss of confidential information.
- Use of personal data without authorization.
- Documents with incorrect information.
- Poorly designed automations.
- Decisions made based on invented or incomplete information.

Therefore, any professional use of Copilot must be based on three principles:

1. **Human control**.
2. **Review of the result**.
3. **Protection of information**.

## 3. Prompt, context and data

To use Copilot safely, we must first differentiate three concepts.

### 3.1 Prompt

The prompt is the instruction that the user writes.

Example:

```text
Resume este documento en cinco puntos principales.
```

Or in development:

```text
Revisa esta función y dime si puede fallar cuando el array está vacío.
```

### 3.2 Context

Context is the additional information that the tool can use to generate a response.

In GitHub Copilot, context can include things like:

- Code close to the cursor.
- Open file.
- Related files.
- Code selection.
- File name.
- Project structure.
- Custom repository instructions, if they exist.

In Microsoft 365 Copilot, the context can be related to:

- Documents.
- Mail.
- Meetings.
- Chats.
- OneDrive or SharePoint files.
- Information available depending on permissions and configuration.

### 3.3 Sensitive data

Sensitive data is data that should not be shared without authorization or sufficient guarantees.

Examples:

- Passwords.
- Tokens.
- API keys.
- Personal data.
- Medical information.
- Financial information.
- Customer data.
- Contracts.
- Proprietary code.
- Internal company information.
- Access credentials.
- Data subject to legal or contractual regulations.

Basic rule:
> If you wouldn't share that information in a public chat or with an outsider, don't paste it into an AI tool without first checking the terms of use, license, and privacy.

## 4. Privacy in the use of Copilot

Copilot tools may function differently depending on the product, license, and environment configuration.

It is not the same to use:

- A personal account.
- An educational account.
- A business account.
- An environment managed by an organization.
- An individual license.
- A corporate license.

Before using Copilot with real information, it is worth checking:

1. What data you can use as context.
2. If the organization allows using that tool.
3. What information can be entered.
4. If there is an internal policy for the use of AI.
5. Whether responses can be stored or reviewed.
6. Whether or not the provider uses the data to train models.
7. What protection measures does the specific license offer.

In class we can work with fictitious examples, simple code fragments and invented data. In a real professional environment, the organization's policy must always be followed.

## 5. Information that we should not enter without authorization

Sensitive information should not be entered into Copilot without clear authorization.

### 5.1 Credentials and secrets

Never hit:

```text
password=...
```

```text
API_KEY=...
```

```text
PRIVATE_TOKEN=...
```

```text
DATABASE_URL=...
```

```text
JWT_SECRET=...
```

If you need help with a credential-related error, replace the actual values with dummy values.

Unsafe example:

```text
Mi conexión falla. Este es mi usuario, contraseña y cadena de conexión real...
```

Safe example:

```text
Mi conexión falla. He sustituido los datos reales por valores ficticios:
DATABASE_URL=postgres://user:password@host:5432/database
¿Qué partes debería revisar?
```

### 5.2 Personal data

Avoid entering data such as:

- DNI.
- Directions.
- Telephones.
- Personal emails.
- Medical data.
- Sensitive work information.
- Customer data.

Safe example:

```text
Tengo una tabla ficticia con columnas name, email y purchaseAmount. ¿Cómo podría anonimizar el campo email antes de analizar los datos?
```

### 5.3 Proprietary code

In professional environments, code may be protected by contracts, confidentiality agreements, or internal policies.

Before pasting real code into an AI tool, check if it is allowed.

If you can't share the code, you can describe the problem abstractly.

Example:

```text
Tengo una función que recibe una lista de pedidos, agrupa por cliente y calcula el total. El problema es que algunos pedidos no tienen cliente asignado. ¿Qué estrategia de validación podría aplicar?
```

## 6. Common risks of AI-generated responses

### 6.1 Hallucinations

A hallucination occurs when AI generates false or fabricated information that appears to be true.

You can invent:

- Functions that do not exist.
- Incorrect parameters.
- Methods of a library.
- Bibliographic references.
- Commands.
- Configuration options.
- Incorrect explanations.

Example:

```text
Usa el método array.removeByCondition() para eliminar elementos.
```

That method does not exist natively in JavaScript. The answer might seem reasonable, but it would be wrong.

### 6.2 Code that works, but is not suitable

Sometimes the generated code is executed, but it is not a good solution.

It can be:

- Poorly readable.
- Difficult to maintain.
- Inefficient.
- Insecure.
- Incompatible with the project style.
- Too complex for the problem.

### 6.3 Lack of context

If Copilot doesn't have enough context, it may propose solutions that don't fit.

For example:

```text
Crea un sistema de autenticación.
```

This request is too broad. Copilot doesn't know:
- What stack is used.
- What database exists.
- What type of users are there.
- What level of security is required.
- Whether sessions or tokens are used.
- If there is already a defined architecture.

A better prompt would be:

```text
Estoy trabajando en una API REST con Node.js y Express. Ya tengo una tabla users con email y passwordHash. Quiero una propuesta para implementar login con JWT, explicando los pasos y señalando riesgos de seguridad. No escribas todavía el código completo.
```

### 6.4 Biases

AI can reproduce biases present in the data with which it was trained or in the instructions received.

In professional contexts, this is especially important in tasks related to:

- Personnel selection.
- Performance evaluation.
- Personalized recommendations.
- Customer service.
- User classification.
- Analysis of sensitive data.

### 6.5 Excessive dependency

If a person accepts all the answers without understanding them, they may lose critical capacity and technical autonomy.

Copilot should help you learn, not prevent you from learning.

A good practice is to ask for explanations:

```text
Explícame esta solución paso a paso y dime qué conceptos necesito entender para mantener este código en el futuro.
```

## 7. Responsible use in software development

When we use GitHub Copilot to code, we should review their proposals using the same criteria as we would review someone else's code.

### 7.1 Generated code review checklist

Before accepting code generated by Copilot, review:

- Do I understand what it does?
- Does it really solve the problem?
- Does it compile or run?
- Is it proven?
-Does it handle errors?
- Does it validate the input data?
- Do you respect the style of the project?
- Does it introduce unnecessary dependencies?
- Do you use existing functions or APIs?
- Could it have security problems?
- Can it break another part of the application?

### 7.2 Review example

Suppose Copilot generates this function:

```javascript
function getUserByEmail(users, email) {
  return users.find((user) => user.email === email);
}
```

The function may seem correct, but we should ask ourselves:

- What happens if users is null?
- What happens if the email comes empty?
- Should you ignore upper and lower case?
- Should it throw an error or return undefined?
- Does the email format have to be validated?

We can ask for an improvement:

```text
Mejora esta función para que valide entradas nulas, compare el email sin distinguir mayúsculas y minúsculas, y mantenga el código simple.
```

A possible improved version would be:

```javascript
function getUserByEmail(users, email) {
  // Validamos que users sea un array y que email tenga contenido
  if (
    !Array.isArray(users) ||
    typeof email !== "string" ||
    email.trim() === ""
  ) {
    return undefined;
  }

  const normalizedEmail = email.trim().toLowerCase();

  return users.find((user) => {
    return (
      typeof user.email === "string" &&
      user.email.toLowerCase() === normalizedEmail
    );
  });
}
```

This version is not automatically perfect, but it shows a more responsible review process.

## 8. Responsible use of documents and productivity

When we use Microsoft Copilot or Microsoft 365 Copilot to work with text, documents, emails, or meetings, we must also review the output.

### 8.1 Frequent risks

- Incomplete summaries.
- Inappropriate tone.
- Loss of important nuances.
- Incorrect interpretation of a meeting.
- Omission of pending tasks.
- Inclusion of unconfirmed information.
- Too generic writing.

### 8.2 Checklist to review generated texts

Before sending or using generated text, check:

- Is the content correct?
- Is the tone appropriate?
- Is important information missing?
- Are there invented data?
- Does the text represent my intention well?
- Have the instructions been respected?
- Is there sensitive information that should not appear?
- Does the text need adaptation to the recipient?

### 8.3 Example of responsible prompt

Instead of asking:

```text
Escribe un correo para mi jefe.
```

It is better to ask:

```text
Redacta un correo profesional y breve para informar de que el informe estará listo mañana. Mantén un tono claro, responsable y sin dar excusas excesivas. No inventes detalles que no te haya dado.
```

## 9. Responsible use in automation and agents
When creating agents or automations, the risks are higher because the system can interact with users or execute actions.

A poorly designed agent can:

- Giving incorrect answers to many people.
- Access information that you shouldn't.
- Execute actions without sufficient control.
- Not knowing when to escalate a person.
- Generate a bad user experience.

### 9.1 Checklist to design agents

Before listing an agent, check:

- What is your exact objective?
- Which users is it aimed at?
- What sources of information can you consult?
- What data should not be shown?
- What actions can you execute?
- When should you say you don't know?
- When should a person escalate?
- Has it been tested with real cases?
- Have borderline cases been tested?
- Is there a way to monitor its operation?

### 9.2 Example of safe instruction for an agent

```text
Eres un agente de soporte interno. Responde únicamente usando la documentación proporcionada. Si no encuentras una respuesta clara, indica que no tienes información suficiente y recomienda contactar con el equipo responsable. No inventes políticas internas ni proporciones datos personales.
```

This statement is safer than a generic statement like:

```text
Responde a cualquier pregunta de los empleados.
```

## 10. Basic ethical principles

The use of Copilot must respect certain ethical principles.

### 10.1 Transparency

In some contexts it may be necessary to indicate that AI has been used as support.

For example:

- Academic documents.
- Corporate reports.
- Regulated processes.
- Production of public content.

### 10.2 Liability

The final responsibility does not lie with Copilot, but with the person or team that decides to use the result.

If Copilot generates an error and we accept it without review, the problem does not disappear because it was generated by an AI.

### 10.3 Data protection

Personal and confidential data must be treated with care.

Real data should not be entered if it is not necessary or if there is no authorization.

### 10.4 Non-discrimination

Possible biases must be monitored, especially when working with sensitive people, profiles, evaluations or decisions.

### 10.5 Human supervision

AI should support decision-making, not completely replace it in important contexts.

## 11. Step-by-step guide to using Copilot safely

### Step 1. Identify the task

Before using Copilot, define what you want to do.

Example:

```text
Quiero refactorizar una función.
```

```text
Quiero resumir un documento.
```

```text
Quiero crear un correo.
```

### Step 2. Decide if you can share context

Ask yourself:

- Is there personal data?
- Are there credentials?
- Is there confidential information?
- Is there a proprietary code?
- Do I have permission to use this information?

If the answer raises doubts, do not paste the actual information.

### Step 3. Anonymize or simplify

Replace real data with fictitious data.

Example:

```text
Cliente real: Empresa XYZ S.L.
```

It can become:

```text
Cliente ficticio: Company A
```

### Step 4. Write a clear prompt

Includes objective, context, restrictions and format.

```text
Analiza esta función ficticia y señala posibles problemas de seguridad. No propongas una solución completa todavía; primero enumera los riesgos principales.
```

### Step 5. Check the answer

Don't accept the result automatically.

Check:

- Accuracy.
- Security.
- Coherence.
- Adaptation to the context.
- Possible omissions.

### Step 6. Ask for clarification

If something is not clear, ask.

```text
Explícame por qué esa solución sería más segura.
```

```text
¿Qué riesgos seguirían existiendo incluso después de aplicar esa corrección?
```

### Step 7. Test before use

In code, run tests.

In documents, review the content.

In automations, try controlled cases.
### Step 8. Document important decisions

If a Copilot proposal affects the project, it is a good idea to document what has been changed and why.

## 12. Examples of safe prompts

### To review code

```text
Revisa esta función y señala posibles problemas de seguridad, rendimiento y legibilidad. No modifiques el código todavía. Primero dame una lista priorizada de problemas.
```

### To refactor

```text
Refactoriza esta función manteniendo exactamente el mismo comportamiento. No añadas nuevas dependencias y explica brevemente cada cambio realizado.
```

### To generate tests

```text
Genera tests unitarios para esta función. Incluye casos normales, casos límite y entradas inválidas. No supongas requisitos que no aparezcan en el código.
```

### To summarize documentation

```text
Resume este documento en lenguaje claro. No añadas información externa y separa el resultado en: ideas principales, dudas abiertas y tareas pendientes.
```

### To work with dummy data

```text
Usa estos datos ficticios para mostrar cómo se calcularía el promedio de ventas por mes. No asumas que representan datos reales.
```

## 13. Examples of unsafe prompts

### Unsafe Prompt 1

```text
Aquí está mi archivo .env completo. Dime por qué falla la conexión.
```

Problem: May include real credentials.

Safer version:

```text
He sustituido los valores reales de mi archivo .env por valores ficticios. Dime qué partes debería revisar si falla la conexión a la base de datos.
```

### Unsafe Prompt 2

```text
Te paso los datos reales de mis clientes para que los analices.
```

Issue: May include personal or sensitive data.

Safer version:

```text
Te paso una muestra ficticia con la misma estructura que mis datos reales. Ayúdame a diseñar un análisis sin usar información personal.
```

### Unsafe Prompt 3

```text
Crea una política interna sobre permisos laborales aunque no tengas más información.
```

Problem: You can make up rules.

Safer version:

```text
Ayúdame a estructurar una política interna sobre permisos laborales. No inventes normas concretas; deja marcados los apartados que deben completarse con información oficial de la empresa.
```

## 14. General responsible use checklist

Before using a Copilot response, review this list:

### Privacy

- Have I entered personal data?
- Have I entered credentials?
- Have I shared confidential information?
- Do I have permission to use this information?
- Can I anonymize the content?

### Security

- Does the code validate entries?
-Does it handle errors?
- Do you avoid exposing secrets?
- Does it introduce unnecessary dependencies?
- Do you respect safe practices?

### Quality

- Does the answer solve the problem?
- Is it understandable?
- Is it adapted to the context?
- Is it maintainable?
- Do you need simplification?

### Verification

- Have I tested the code?
- Have I reviewed the text?
- Have I checked the sources for external data?
- Have I asked for clarifications if something is not clear?

### Responsibility

- Can I explain the result in my own words?
- Am I willing to accept this change as my own?
- Have I documented what is important?

## 15. Summary of the topic

Copilot can be a very powerful tool, but it must be used responsibly. The responses generated may contain errors, biases, fabricated information, or unsafe solutions. Furthermore, the use of personal data, credentials or confidential information requires special care.

The main idea of ​​this topic is that Copilot should be used as an assistant, not the final authority. The user must review, test, adapt and validate any results before incorporating them into a project, document or professional process.

Using Copilot well isn't just about asking it for things. It involves knowing what to ask for, what not to share, how to review the response, and when not to accept a proposal.
